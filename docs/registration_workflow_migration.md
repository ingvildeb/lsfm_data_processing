# Registration Workflow Migration Ledger

This file tracks temporary compatibility behavior introduced while project
repositories migrate to the shared registration workflow. Compatibility code
must not be removed until its stated removal condition is satisfied.

| Temporary behavior | Required by | Canonical replacement | Removal condition |
| --- | --- | --- | --- |
| Accept missing or schema-1 native-image provenance and record `adopted_existing_unverified_source_link` | Existing SING, Glia Mapping, Triple Transgenic, and Chandelier native images | Deterministic schema-2 per-image provenance | All active native images have schema-2 provenance and all four projects use shared preparation |
| Replace legacy header-validation and provenance sidecars during adoption | Existing prepared batches | Immutable deterministic sidecars | Legacy adoption support is removed |
| Project-local preparation adapters | Project-specific paths, channels, ages, and filenames | Shared preparation planner/applicator plus thin project adapters | All four projects have parity tests and no copied preparation machinery |
| Verify matching `batchXXX_input.xlsx` and `batchXXX_subjects.xlsx`, create `batchXXX.xlsx` plus `batch_manifest.json`, then retire the duplicates | Existing project batches | One canonical workbook and immutable normalized membership manifest | Every active batch has the canonical workbook and manifest |
| Retain an existing baseline TOML when it is structurally equal to the shared rendering, and mark it adopted in provenance | Existing batches generated by project-local renderers | Shared baseline renderer and provenance | Every active baseline was generated through the shared workflow |

Chandelier Cell has completed its batch membership migration and now requires
`batch_manifest.json` for cross-batch auditing. The shared package continues to
accept matching legacy `batchXXX_input.xlsx` and `batchXXX_subjects.xlsx` pairs
when migrating older project batches, including Glia Mapping batches.

Compatibility paths must have explicit tests. Remove the implementation,
ledger row, and compatibility tests together after the removal condition is met.
